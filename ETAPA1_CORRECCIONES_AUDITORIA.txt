ARCHIVO: supabase/migrations/20260724162700_initial_schema.sql
-----------------------------------------------------------------------------

PROBLEMA ANTERIOR:
El orden de los permisos era incorrecto:
1. Se concedía EXECUTE a authenticated
2. Luego se revocaba ALL al schema _private de authenticated
3. Esto dejaba la función inaccesible porque no hay USAGE en el schema

SOLUCIÓN APLICADA:
Nuevo orden correcto de permisos:

  -- 1. Revocar todo por defecto
  REVOKE ALL ON SCHEMA _private FROM PUBLIC;
  REVOKE ALL ON SCHEMA _private FROM anon;
  REVOKE ALL ON SCHEMA _private FROM authenticated;
  
  -- 2. Crear función SECURITY DEFINER con search_path seguro
  CREATE OR REPLACE FUNCTION _private.user_belongs_to_family(...)
  ... LANGUAGE plpgsql SECURITY DEFINER SET search_path = '';
  
  -- 3. Conceder USAGE del schema (necesario para encontrar la función)
  GRANT USAGE ON SCHEMA _private TO authenticated;
  
  -- 4. Conceder solo EXECUTE de la función específica
  REVOKE ALL ON FUNCTION _private.user_belongs_to_family(UUID, UUID) FROM PUBLIC;
  REVOKE ALL ON FUNCTION _private.user_belongs_to_family(UUID, UUID) FROM anon;
  GRANT EXECUTE ON FUNCTION _private.user_belongs_to_family(UUID, UUID) TO authenticated;

JUSTIFICACIÓN TÉCNICA:
- Para invocar una función en un schema, se necesita USAGE en el schema
- SECURITY DEFINER con search_path = '' previene inyección de schema
- Los permisos se conceden explícitamente después de revocar por defecto
- No se usa service_role ni claves administrativas

VERIFICACIÓN POSTERIOR:
Los tests SQL ahora incluyen:
- TEST 8: has_function_privilege('authenticated', ..., 'EXECUTE') = true
- TEST 9: has_schema_privilege('authenticated', ..., 'USAGE') = true
- Ambos deben retornar true para considerar la configuración correcta

ARCHIVO: supabase/tests/database/test_rls_isolation.sql
-----------------------------------------------------------------------------

PROBLEMA ANTERIOR:
- Usaba relpolicies IS NOT NULL (incorrecto para verificar RLS)
- Casos de integración solo como comentarios sin estructura de test
- Sin verificaciones de permisos de función/schema

SOLUCIÓN APLICADA:
9 tests estáticos verificables que consultan catálogos PostgreSQL:

TEST 1: RLS habilitado en todas las tablas
  - Consulta: pg_class.relrowsecurity
  - Esperado: 8 tablas con relrowsecurity = true

TEST 2: Políticas existen para todas las tablas
  - Consulta: pg_policies COUNT por tabla
  - Esperado: policy_count >= 1 para cada tabla

TEST 3: Roles de políticas son solo 'authenticated'
  - Consulta: pg_policies.roles
  - Esperado: Todas las políticas contienen 'authenticated'
  - Esperado: Ninguna política contiene 'anon' o 'public'

TEST 4: Función SECURITY DEFINER configurada correctamente
  - Consulta: pg_proc.prosecdef, proconfig
  - Esperado: prosecdef = true, proconfig contiene 'search_path='

TEST 5: CHECK constraint en expenses.amount_clp
  - Consulta: pg_constraint para expenses
  - Esperado: constraint_def LIKE '%amount_clp >= 0%'

TEST 6: CHECK constraints en products.stock
  - Consulta: pg_constraint para products
  - Esperado: current_stock >= 0 AND minimum_stock >= 0

TEST 7: Schema _private existe
  - Consulta: pg_namespace WHERE nspname = '_private'
  - Esperado: 1 fila retornada

TEST 8: Permisos de función correctos
  - Consulta: has_function_privilege()
  - Esperado: authenticated=true, public=false, anon=false

TEST 9: Permisos de schema correctos
  - Consulta: has_schema_privilege()
  - Esperado: authenticated=true, public=false, anon=false
